# keel

**The structure you lay down before you build anything.**

A keel is the first timber laid when building a ship. Everything else is fastened to it, and it's what keeps the thing upright in weather.

This is a template repo for building software with an AI coding agent. It is not a framework — nothing imports it, nothing runs unless you type a command. It's a set of files that give a project a spine: rules the agent follows, gates that fail when work is sloppy, and a paper trail so you can always answer *what's broken*, *what happened*, and *why did we do it that way*.

It works for any language and any stack, because the only stack-aware file is `keel.config.json`.

---

## Why

Coding agents are fast and have no memory. Left alone they produce work that looks finished, drifts from its own rules, and leaves no trace of the reasoning. The usual fix is a long instructions file, which rots, and heroic vigilance, which doesn't scale.

keel's position is narrow:

> **A rule that isn't enforced is a wish.**

So the rules live in three places, in increasing order of trustworthiness:

1. `CLAUDE.md` — prose the agent reads (weakest; useful, ignorable)
2. **Ratchets** — CI fails if a number gets worse (strong)
3. **Coverage gates** — a test that fails when someone bypasses a rule (strongest)

Everything else in this repo exists to make those three cheap to set up on day one.

## Quickstart

```bash
gh repo create my-project --template ltg220/keel --private --clone
cd my-project
```

Then open Claude Code and run:

```
/keel-init
```

It interviews you about what you're building, recommends a stack, records **why** in `docs/decisions/0001-stack.md`, generates your `CLAUDE.md`, wires the real test runner and CI, and picks your tier. Ten minutes later `node scripts/gates.mjs` is green on an empty project.

From there, per feature:

```
/keel-spec "trainer battles"   →  docs/specs/trainer-battles.md
/keel-plan                     →  .claude/plans/trainer-battles.md
/keel-implement                →  task 1 → check → task 2 → check → …
/keel-review                   →  adversarial pass over the diff
/keel-ship                     →  commit + report + PR
```

Any time:

```
/keel-prime    load context before working
/keel-map      regenerate docs/architecture.md from the code
/keel-audit    do the docs still match reality?
/keel-loop     run unattended: pull from the queue, stop at the PR
```

## Tiers

The most common failure with a setup like this is applying production discipline to a weekend project, hating it, and abandoning the whole thing. So keel scales down.

| Tier | Intent | What runs |
|---|---|---|
| **L1** | Prototype. **Mess is allowed.** | Tests + typecheck. Nothing blocks you |
| **L2** | Product. Mess is flagged. | + lint, ratchet, known-issues, 1 review round, handoffs |
| **L3** | Production. Mess is blocked. | + coverage gates, 2 adversarial rounds, architecture drift check, full audit |

`/keel-init` picks the tier for you from the interview. You can override it in `keel.config.json`, but the default is deliberate — the point is not to make you choose.

L1 saying "mess is allowed" is load-bearing. Prototypes should be fast, and guilt makes people set everything to L3 and then quit.

## What's in the box

```
keel.config.json          the brain — tier, stack, gate commands
CLAUDE.md                 durable rules (no dated status — that rots)

.claude/skills/           the recipe cards the agent follows
.claude/plans/            plan files, so work survives a dead session
.claude/reports/          what actually happened (becomes the PR body)

docs/rules.md             coding standards
docs/known-issues.md      what's broken right now
docs/decisions/           ADRs — why we chose this, and what would change our mind
docs/designs/             design docs for in-flight work, incl. rejected alternatives
docs/runbooks/            it broke — what do I do
docs/handoffs/            dated log of sessions, newest first
docs/testing.md           what "green" means here
docs/architecture.md      generated by /keel-map, never hand-maintained
docs/secrets.md           inventory of secret NAMES and where values live. Never values
docs/roadmap.md           what's next
docs/archive/             completed work, so the live docs stay short

scripts/gates.mjs         stack-agnostic gate runner
scripts/ratchet.mjs       blocks new debt; ratchets down only
scripts/doctor.mjs        is this repo still internally consistent?
scripts/worktree.sh       parallel lanes without cross-session bleed

tasks/queue.md            the outer-loop work queue
```

## The two loops

**Inner loop** — one feature, you're present:

```
plan → task 1 → its check → task 2 → its check → … → done
```

The rule that makes it work: **every task in the plan carries its own validation command, and a task is not done until its check passes.** Errors get caught at task 3, not at task 11.

**Outer loop** — many features, you're asleep:

```
pick from queue → inner loop → gates → review → open PR → stop
```

Four safety properties, all non-negotiable:

- **Timer, not webhooks.** Polls on a schedule. Simple to reason about, trivial to stop.
- **Protected files, enforced by a hook.** `scripts/guard.mjs` runs as a `PreToolUse` hook and blocks any Edit, Write, or Bash call that would modify a path in `loop.protected`. A hardcoded floor — the rulebook, the config, the hook wiring, and the guard itself — holds even if the config is emptied or corrupted. `doctor` fails if the hook is unregistered. Direct file edits are blocked deterministically; shell commands are caught by a conservative heuristic (see Honest limits).
- **Autonomy dial (0–5).** One number decides what it's allowed to do. Raised by you, never by it.
- **It never merges.** The loop stops at the pull request. Always.

That last one isn't caution, it's the current state of the art: autonomous agents close every pre-merge stage, and the boundary is merge.

## What keel deliberately is not

- **Not a framework.** No dependency, no import, no runtime. Delete any file and the rest still works.
- **Not multi-agent.** One agent, plus targeted subagents for review. Multi-persona swarms add orchestration surface that is markedly harder to debug when it goes wrong, and keel is optimised for a small team or one person.
- **Not a stack.** `keel.config.json` is the only file that knows what you're building with.
- **Not auto-merge.** See above.

## Honest limits

Things a skeptical reader should know before trusting any of the above.

**The template is mostly prose, and prose is the layer keel itself calls weakest.** The
ratchet ships with no metrics and coverage gates are L3-only, so what you clone is largely
rules-as-text. The enforcement is generated per project by `/keel-init`. That is a real
concession: until you initialise, the strong layers are potential rather than present.

**Two rules cannot be mechanically enforced, and they are important ones.** "A test must
exercise the path it claims to" and "say what actually happened" are claims about the agent's
own honesty, and no gate can check them. Worse, `.claude/reports/` is agent-authored evidence
about agent behaviour, promoted into the pull request body. Treat the gates as the objective
signal and the report as testimony.

**The Bash side of the guard is a heuristic.** Edit, Write, and NotebookEdit are matched on
the exact path and blocked deterministically. Shell commands cannot be parsed reliably, so the
guard blocks when a command both mentions a protected path and looks like a write. It errs
toward blocking, and a determined workaround would get through. The floor and the hook close
the accident case, not an adversary.

**It needs Node, whatever you are building.** `gates.mjs`, `ratchet.mjs`, and `doctor.mjs` are
plain JavaScript with no dependencies, but a Python or Go project still needs Node installed to
run its own gates. That was the price of a harness that runs on a clean clone with no install
step — see `docs/decisions/0001-harness-language.md`.

**Moving state out of the rulebook does not stop it rotting.** `CLAUDE.md` bans dated state
because state rots; the state then lives in `known-issues.md` and `handoffs/`, which rot too.
Two things soften this: those files are explicitly labelled as hypotheses to verify rather
than truth, and `doctor` warns when they fall behind the commit history. Only
`docs/architecture.md` gets the real fix, which is being generated rather than maintained.

**It is new.** There is no example project yet, and the ideas here have more mileage than this
particular implementation of them.

## Prior art

keel is assembled from ideas that already work, not invented from nothing:

- **[GitHub Spec Kit](https://github.com/github/spec-kit)** — the spec → plan → tasks → implement shape, and the idea of a project "constitution." keel copies the shape rather than depending on the tool.
- **[coleam00/skills](https://github.com/coleam00/skills)** — the PIV loop, per-task validation gates, worktree fan-out, and the dark-factory safety layer (protected files, autonomy levels, stop button). keel takes all of that except auto-merge.
- **Enterprise Integration Patterns** — the claim-check idea behind keeping large payloads out of state.

What keel adds that those don't ship: the **memory layer** (known-issues + handoffs + decisions), **adversarial review as a required gate**, and **rules with teeth** (ratchets and coverage gates rather than prose).
